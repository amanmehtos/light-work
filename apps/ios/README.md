# Light Week on iPhone

## Status, plainly

**LightKit compiles and its tests pass.** It was written in a Linux container
with no Swift toolchain, and this README used to warn that none of it had ever
been built. It has now been built on a Mac, on the first attempt, with no
changes needed — the warning was pessimistic and has been removed rather than
left to make the package look riskier than it is.

Its clock encoding is now checked against **vectors generated by
`packages/core/src/hlc.ts`** rather than against expectations written by hand.
That was the one real drift risk and the old test could not have caught it: it
asserted the shape (three colon-separated parts, survives a round trip), which
stays true even if the padding widths are wrong — and the padding is the whole
point, since it is what makes a clock sort correctly as a string.

**The app signs in, lists tasks, and starts a focus block.** You can sign in
over OAuth+PKCE, see your open tasks with the focus already spent on each, and
tap Focus to land in Light Minute with that task bound — which is the arc the
suite exists for, and until now nothing anywhere emitted its second half.
`LightWeek.xcodeproj` uses Xcode 16+ *synchronized folders*, so every file under
`LightWeek/` joins the target automatically and adding Swift files never means
editing `project.pbxproj`.

| File | What it does |
| --- | --- |
| `Services/LightWeek.swift` | Which server, which client id, which redirect |
| `Services/LightWeekAuth.swift` | The authorization code flow, and the grant in the Keychain |
| `Services/FocusHandoff.swift` | The `com.lightminute.app:/focus?…` link |
| `ViewModels/TaskListModel.swift` | The snapshot, turned into rows with focus totals |
| `Views/` | The list, the row, the sign-in screen, the badges |

The OAuth flow is **ported from Light Minute's**, which was driven against both
the deployed worker and the real request handler before this existed. The client
id, the scheme and the redirect differ; the handshake does not. Two
implementations of one set of security checks is two sets to get wrong.

What is still read-then-render against `/sync/snapshot`, not the local-first
replica the web client has — see below.

## LightKit

A Swift package both Light Minute and the eventual Light Week app depend on, so
neither invents its own idea of what a focus session is.

| File | What it holds |
| --- | --- |
| `Model.swift` | The domain types, mirroring `packages/core/src/entities.ts` field for field |
| `Clock.swift` | The hybrid logical clock, encoding identically to the TypeScript one |
| `Protocol.swift` | Wire types for the sync protocol |
| `LightWeekClient.swift` | Sign in, read the account, write focus sessions |

Two things in here are easy to get wrong and so are tested:

**The clock must encode identically across platforms.** The padded base-36 form
is what lets a timestamp sort as a string. If iOS pads differently, clocks sort
differently on the server and conflict resolution quietly stops matching.

**Priority 1 is urgent**, matching the p1 a user reads — the opposite of
Todoist's internal scale.

## Wiring up Light Minute

When a timer finishes:

```swift
let client = LightWeekClient(baseURL: URL(string: "https://api.lightweek.app")!,
                             token: storedToken)

try await client.log(FocusSession(
    taskId: selectedTask?.id,
    startedAt: startedAt,
    endedAt: Date(),
    plannedSeconds: 25 * 60,
    focusedSeconds: actualFocusedSeconds,   // excluding paused time
    interruptions: pauseCount,
    outcome: wasCompleted ? .completed : .abandoned,
    source: "light-minute-ios"))
```

And to let someone pick what they are about to focus on:

```swift
let tasks = try await client.openTasks()   // open only, urgent first
```

That is the whole integration. Light Week does the rest: it shows accumulated
focus time on each task, and the MCP server hands that data to an agent so
planning can account for where attention actually went.

`completeTask` exists but deliberately does **not** handle recurrence — a
recurring task completed through it is marked done rather than rescheduled.
Recurrence lives in `@light/client-sdk`, and Light Minute has no business
rescheduling someone's repeating task.

## What still needs doing

1. **The local-first replica.** The task list reads `/sync/snapshot` on
   appearance and renders it. That is honest while nothing in the app writes,
   but it means no offline list and no live update — the store, the merge rule
   and the queue from `@light/core` are what the web client has and this
   eventually wants.
2. **Writing.** The grant asks for `tasks:write` because completing a task from
   the list is the obvious next thing, and a scope widened later means a second
   consent screen. Nothing uses it yet.
3. **A real sign-in against the deployed server.** Everything here was driven
   against the real request handler running in memory with a seeded account.
   The deployed worker's own consent screen needs the owner's Google account
   and their tap, and has not been through.

**Two sign-ins, not one.** A free Personal Team cannot enable App Groups, so
Light Week and Light Minute each hold their own grant in their own Keychain
item: two consent screens, and nothing to share. An earlier version of this
README called for one shared item; it is not available on this team.

**Cross-platform clock tests** are done — the Swift tests now check the
encoding against vectors generated by `packages/core/src/hlc.ts`.
